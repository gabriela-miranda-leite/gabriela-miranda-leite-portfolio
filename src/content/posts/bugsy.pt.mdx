# Bugsy: um overlay de debug que cabe no bolso

Enquanto construía um projeto pessoal, senti falta de uma ferramenta de debug embutida no próprio app, algo que fosse além do Logcat ou de proxies externos. Ao longo da minha experiência trabalhando com apps mobile em produção, acostumei-me ao ganho de produtividade que boas ferramentas internas de inspeção trazem para o dia a dia de devs e QAs.

Quando me vi sem essa estrutura fora do trabalho, decidi construir a minha própria. Mas fui além da inspeção de chamadas de rede: eu queria conseguir mockar respostas, alternar flags e simular cenários de erro direto no celular, sem depender de backend ou recompilar o app.

### O que é a Bugsy

A Bugsy é uma biblioteca Kotlin Multiplatform (Android e iOS) que adiciona um painel de debug embutido no próprio app. Ela funciona como um overlay (uma camada visual flutuante que aparece sobre o app ao agitar o celular, sem substituir a tela aberta), na mesma linha de ferramentas como Chucker e Flipper, com quatro módulos principais: inspeção de requisições de rede em tempo real, mocks de resposta, feature flags e informações do dispositivo.

![Mapa das funcionalidades da Bugsy a partir do app Android/iOS: controlar flags (liga/desliga estados), dados do app (e-mail, documento e outros dados úteis), visualizar requests (detalhes, exportação em .har e mock a partir da request) e mockar requisições (importar/exportar, mock de execução única e configuração de body, header e status)](/posts/bugsy/funcionalidades.png)

Tudo isso sob uma política estrita: “quando em dúvida, mascara”. Tokens, senhas e dados sensíveis como CPF nunca ficam expostos em tela por padrão.

### A dor real por trás da aba de Mocks

Inspecionar o que entra e sai na rede resolve metade do problema. Reproduzir cenários específicos é o outro gargalo.

Como desenvolvedora mobile, já passei várias vezes por situações em que o requisito era garantir que uma tela de feedback aparecesse caso a requisição demorasse mais que um determinado tempo. Testar isso na prática raramente era simples: colocar um delay artificial no código da build, mandar para validação e depois lembrar de remover, ou pedir uma adaptação temporária no backend. Um fluxo complexo e propenso a erro apenas para validar um comportamento visual.

O mesmo problema aparece em produtos cheios de regras de negócio. Nem sempre o backend consegue gerar rapidamente a massa de dados exata para um cenário específico. Existem ferramentas como o Mockoon para simular respostas localmente, mas quando a necessidade vai para um QA, PM ou PO validar no celular, exigir configuração de proxy e servidor local cria uma barreira técnica desnecessária.

Foi para eliminar esse atrito que nasceu a aba de Mocks da Bugsy. Qualquer pessoa com o app de debug instalado consegue criar regras que interceptam chamadas combinando método HTTP com um padrão de URL em regex, devolvendo status, headers e body customizados direto no dispositivo, sem tocar no servidor.

Três recursos tornam esse fluxo acessível para todo o time:

- **Criação a partir de chamadas reais:** Com “Create mock from this response”, basta selecionar uma requisição que acabou de passar pela rede para preencher a regra automaticamente. A partir daí, qualquer pessoa altera apenas o status ou o campo do JSON necessário para simular o cenário desejado.
- **Controle de tempo e execução:** Cada regra permite configurar um delay simulado para validar loadings e timeouts sem alterar uma linha de código, além do modo one-shot, que aplica o mock apenas na próxima requisição e volta ao fluxo normal em seguida.
- **Compartilhamento via JSON:** As regras podem ser exportadas e importadas como arquivos JSON. Se um QA encontra um bug em uma condição específica de resposta, exporta a regra e manda para o dev reproduzir o mesmo comportamento em segundos.

### Sob o capô: arquitetura KMP e decisões técnicas

Para que a Bugsy funcionasse de forma consistente nos dois sistemas sem virar um peso na base de código do app hospedeiro, a arquitetura foi dividida em três módulos independentes: `:core`, `:ui` e `:bugsy-noop`.

O módulo `:core` concentra o motor da biblioteca: gerenciamento de estado, motor de regras de mock, feature flags e a abstração da camada de rede. A interceptação acontece de forma nativa, usando um interceptor OkHttp no Android e `NSURLProtocol` no iOS, mas ambos convertem os dados capturados para um modelo único compartilhado em Kotlin.

O módulo `:ui` consome esse estado compartilhado para renderizar o overlay em Compose Multiplatform. Toda a interface (inspeção de requisições, edição de regras de mock, flags e informações do dispositivo) é escrita uma única vez, com a mesma experiência visual nas duas plataformas.

O terceiro módulo, `:bugsy-noop`, existe por segurança e higiene de build. Ele expõe exatamente a mesma API pública da biblioteca, mas com implementações vazias e zero instrumentação. O app usa a versão completa em desenvolvimento e homologação, e troca pela dependência no-op na build de release, sem condicionais de ambiente espalhados pelo código do projeto.

![Fluxograma da arquitetura da Bugsy: OkHttp Interceptor (Android) e NSURLProtocol (iOS) alimentam o módulo :core (captura, mock engine, mascaramento e flags), que alimenta o :ui em Compose Multiplatform; na build da release, o :bugsy-noop substitui tudo com a mesma API e zero código](/posts/bugsy/fluxograma.png)

A política de privacidade por padrão foi inegociável desde o início. Ferramentas de debug geram prints, vídeos de evidência de bug, logs compartilhados no Slack. Se um token ou CPF aparecer em texto limpo, o risco de vazamento acidental é imediato. Por isso o `:core` aplica o mascaramento direto na captura dos payloads e headers, exigindo uma ação explícita para revelar qualquer dado sensível.

### Blindagem de release

Qualquer engenheira que já trabalhou com apps em escala olha para uma biblioteca de debug e faz a mesma pergunta: e se isso vazar para a loja, ou quebrar o build na geração da versão de produção? Tratar essa preocupação como prioridade desde o primeiro dia foi essencial.

O ponto crítico em bibliotecas com padrão no-op é a divergência de assinaturas. É comum adicionar um método novo no módulo principal e esquecer de replicar na versão vazia, descobrindo o erro só quando a esteira tenta compilar o release. Para eliminar esse risco, a Bugsy tem um contrato de paridade chamado `ApiSurface.kt`, que força o `:bugsy-noop` a manter exatamente a mesma assinatura pública dos módulos `:core` e `:ui`. Qualquer discrepância quebra a compilação antes do código ir para revisão.

Além disso, gates automatizados na esteira de CI/CD garantem que nenhum rastro de instrumentação chegue ao usuário final:

- **Auditoria do binário final:** O script `check-release-clean.sh` inspeciona o APK de release para validar que nenhuma classe de overlay, motor de mock ou código de debug foi empacotado por engano.
- **Regressão visual e segurança:** Antes de qualquer artefato subir para o Maven Central, a esteira executa testes de screenshot com Paparazzi, análises estáticas de segurança e validações em emulador Android e simulador iOS.

### Próximos passos

A Bugsy já está disponível no Maven Central para projetos Kotlin Multiplatform, Android e iOS. Os próximos passos incluem suporte a React Native e Flutter, e uma interface para acompanhar o debug pelo computador, o que deve trazer ainda mais praticidade para o fluxo de desenvolvimento e validação do time.
